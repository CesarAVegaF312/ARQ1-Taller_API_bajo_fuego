API bajo fuego

La API de pedidos de Inventarium funciona en la demo: cada petición, enviada una vez y con buena red, responde bien. En este taller la auditan, la ponen frente a una red móvil que pierde respuestas y rediseñan su contrato hasta que el mismo caos deje de cobrar dos veces.

Una API puede responder bien a cada petición y aun así cobrar dos veces. Lo que lo evita no está en el código de cada endpoint: está en el contrato. Qué se puede reintentar, qué se puede cachear y qué significa cada código.

v0 · lo que hay

Siete endpoints con verbos en la URI, errores escondidos en 200 y un GET que cancela pedidos.

La red · lo que pasa

Latencia, respuestas que se pierden después de que el servidor ya procesó y clientes que reintentan.

v1 · lo que ustedes diseñan

Seis decisiones de contrato. Cada una cambia el comportamiento real del servidor simulado.

Los consumidores

La misma capacidad para cinco consumidores distintos. No todos deben recibirla igual.

01

Auditoría: qué hace realmente la API v0

Esta es la API que el proveedor entregó. Pruébenla como lo haría un cliente: peticiones válidas, inválidas, repetidas y sobre recursos que no existen. Cada defecto que registren debe citar una petición del historial; sin evidencia no cuenta. Hay pedidos de prueba con id 1001, 1002 (ya pagado) y 1003.

Endpoints v0

GET /getProductos
GET /getProducto?id=SKU-…
POST /crearPedido
GET /pedido?id=…
POST /pagarPedido
GET /cancelarPedido?id=…
POST /actualizarPedido

Qué mirar

  • La URI: ¿identifica un recurso o nombra un procedimiento?
  • El método: ¿es seguro? ¿es idempotente? ¿coincide con lo que hace?
  • El código: ¿un intermediario entendería el resultado sin leer el cuerpo?
  • Los encabezados: ¿hay algo que permita cachear o revalidar?
  • La repetición: ¿qué pasa si envían lo mismo dos veces?

La red miente

Ahora la v0 recibe clientes móviles reales: miran el catálogo varias veces, crean un pedido y lo pagan. La red tiene latencia y a veces pierde la respuesta después de que el servidor ya procesó. El cliente no sabe si su petición llegó; solo sabe que no recibió respuesta, y reintenta. Toda la clase usa la misma semilla, así que con los mismos parámetros todos ven los mismos números.

La misma capacidad, cinco consumidores

La capacidad es una sola: consultar y crear pedidos de Inventarium, con las reglas que acaban de diseñar. Pero no la consume un solo cliente. Para cada uno de estos cinco consumidores, elijan cómo exponérsela y justifiquen la elección en una línea. Varias respuestas son defendibles; algunas fallan por razones concretas. Las consecuencias se revelan cuando el grupo haya elegido y justificado las cinco.

MCP es un estilo de integración, no un patrón. Model Context Protocol define cómo una aplicación con un modelo de lenguaje descubre y usa capacidades externas: tools (acciones), resources (datos para leer) y prompts (plantillas), con mensajes JSON-RPC 2.0 sobre stdio o Streamable HTTP. No decide cómo se organiza el sistema. En la práctica es un adaptador más sobre la API que ya existe: se genera desde el mismo contrato, aplica las mismas reglas de negocio y convive con los demás consumidores. Es un adaptador de entrada en el sentido de la arquitectura hexagonal del módulo 5: un puerto nuevo, el mismo núcleo. El Technology Radar de Thoughtworks (vol. 34, abril de 2026) advierte contra «MCP by default»: exponerlo todo por MCP porque sí, sin un consumidor que lo necesite.
El puente con la ronda 3. Un agente reintenta por diseño: si una herramienta no responde o la respuesta no le sirve, vuelve a llamarla. Si la escritura que hay detrás no es idempotente, el agente cobra dos veces, igual que la app móvil de la ronda 2, pero sin una persona que lo note en pantalla. Cuando el consumidor es un agente, la Idempotency-Key en toda escritura deja de ser una buena práctica y pasa a ser requisito.
